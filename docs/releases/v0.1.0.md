# Hachures `v0.1.0`

**Status:** planned milestone  
**Release type:** first technical playable release  
**Version source:** `game/Cargo.toml`

## Objective

Deliver a reliable, playable, and portfolio-ready technical release without claiming that every
post-game feature from `docs/bible.md` is complete.

## Included scope

- Current playable campaign through Worlds 1–6
- Save and progression systems
- French and English localization
- CI/CD workflows and local validation
- Native packages for Linux x86_64, macOS Apple Silicon, macOS Intel, and Windows x86_64
- Browser package with HTTP/package smoke validation

## Acceptance criteria

- [x] The included campaign starts, can be played through World 6, and persists progress.
- [x] French and English localization validation passes.
- [ ] Native packages build and start on all supported platforms.
- [x] The browser package builds and passes its package/HTTP smoke test.
- [x] `cargo fmt --check` passes.
- [x] `cargo clippy --all-targets -- -D warnings` passes.
- [x] `cargo test -p game --quiet` passes.
- [x] `cargo test -p game balance -- --ignored` passes.
- [x] `cargo check --target wasm32-unknown-unknown -p game` passes.
- [ ] No generated output, secret, or unreviewed asset is included.
- [ ] GitHub CI is green for the release candidate.
- [ ] Release notes and the tagged build describe the same scope.

## Known limitations

These are intentionally outside the `v0.1.0` release blocker list:

- Bonus sheets are data foundations, not fully integrated post-game content.
- Signer is a safe preview foundation, without the complete import/export editor workflow.
- Heroic mode is incomplete.
- The four ending consequences are not fully implemented.
- Treuil and defection branches remain incomplete.
- The advanced audio and final art passes remain future work.

These limitations must be repeated in the GitHub Release and portfolio documentation.

## Release procedure

1. Complete the acceptance checklist on `release/v0.1.0`.
2. Update this file with the final validation results and commit references.
3. Merge `release/v0.1.0` into `main`.
4. Create an annotated tag on the merge commit:

   ```sh
   git tag -a v0.1.0 -m "Hachures v0.1.0"
   git push origin main v0.1.0
   ```

5. Publish the GitHub Release with native and browser packages.
6. Merge the release branch back into `develop`.

The tag must never be moved. A correction requires a new patch release such as `v0.1.1`.
